SAFE vs VULNERABLE OUTPUT — READ-ONLY CHECKS
================================================

Screenshot context:
- SQL Server 2019
- Build shown: 15.0.4480.2
- Enterprise Edition
- SSMS connection

IMPORTANT:
- Run only on explicitly authorized systems.
- "VULNERABLE/POTENTIAL" means investigate/report only after validating
  business requirement, scope, exploitability and impact.
- Commands are intentionally read-only.
- Do NOT extract/crack password hashes, recover credential secrets, export
  private keys, dump sensitive data, execute OS commands, modify permissions,
  modify jobs, or change SQL Server configuration unless explicitly authorized.
- Run the database-level commands in EVERY in-scope database, not just master.

================================================================
CRITICAL CHECKS YOU SPECIFICALLY ASKED FOR
================================================================

1) ALL USERS' ACCESS:
- sys.server_role_members
- sys.server_permissions
- sys.database_role_members (run in every DB)
- sys.database_permissions (run in every DB)
- PUBLIC permissions
- GUEST
- IMPERSONATE
- orphaned users

2) STORED CREDENTIALS:
- sys.credentials
- SQL Agent proxies
- database_scoped_credentials
- linked servers
- external data sources
- sensitive column inventory
Metadata is safe to enumerate. Do not retrieve secrets/hashes/private keys.

3) CLEAR-TEXT NETWORK TRAFFIC:
Use sys.dm_exec_connections and check:
    net_transport = TCP
    encrypt_option = TRUE

If an in-scope remote TCP connection has:
    encrypt_option = FALSE
while TLS/encryption is required by policy,
that is a potential clear-text SQL traffic finding.

Also verify SQL Server Configuration Manager:
Protocols for <instance> -> Flags -> Force Encryption.

4) MISCONFIGURATION:
Check:
- xp_cmdshell
- Ole Automation Procedures
- Ad Hoc Distributed Queries
- CLR / CLR strict security
- TRUSTWORTHY
- cross database ownership chaining
- contained database authentication
- remote admin connections
- SQL Agent
- linked-server RPC/data access
- SA status
- service account
- auditing
- TDE/database encryption

================================================================
DO NOT CONFUSE THESE
================================================================

encrypt_option = TRUE
    = network connection encryption for that SQL connection.

is_encrypted = 1
    = database encryption status (e.g. TDE), NOT proof that network traffic
      is encrypted.

Kerberos
    = authentication mechanism, NOT the same thing as TLS encryption.

Shared Memory
    = local SQL Server connection; do not treat it as a remote clear-text
      network connection.

================================================================
REPORTING RULE
================================================================

A finding should normally contain:
- Title
- Affected server/database/account
- Evidence/output
- Expected secure configuration
- Observed configuration
- Security impact
- Severity/CVSS according to engagement methodology
- Remediation
- Business justification/exception if applicable

Never call a configuration "vulnerable" only because it is enabled. Confirm
whether it is required and whether the tested account can actually abuse it.
